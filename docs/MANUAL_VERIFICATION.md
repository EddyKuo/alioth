# 需要實機或外部資源的驗收項目

| 項目 | 內容 |
|---|---|
| 對應 WBS | 7.10（勾稽矩陣的補充） |
| 維護方式 | 手動；每完成一項就在 `tools/traceability.py` 更新對應需求的狀態與備註 |

## 這份文件存在的理由

`docs/TRACEABILITY.md` 裡有一批需求長期停在「部分」，備註寫著「未實機驗證」。
那個描述是誠實的，但對要驗收的人沒有用——他不知道**要做什麼**才算驗過。

留著一句「未驗證」而不寫下步驟，實際效果是這幾項永遠不會被驗：每個接手的人
都得重新推導一次該怎麼測，而推導的成本高到不如先做別的。

以下每一項都寫成可以照著執行的步驟，並明確定義「通過」的判準。所有項目都
**不需要改程式碼**——程式端已經完成，缺的是一台有對應硬體或外部服務的機器。

---

## 1. Acrobat 相容性（PRD-ANN-001 / ANN-005 / SIG-004）

**為什麼自動化測不到**：qpdf 只驗結構合法，PDFium 只驗我們自己讀得回來。
「Acrobat 開起來長什麼樣」需要 Acrobat，而 CLAUDE.md 把它列為
「全案最高風險節點的最終裁決者」。

**需要**：Adobe Acrobat Reader（免費版即可，簽章與註解顯示不需要 Pro）。

**步驟**

1. 以 `tests/` 的語料建立一份含以下全部元素的 PDF（可用本程式逐一加）：
   螢光筆、底線、刪除線、波浪線、矩形、橢圓、直線、箭頭、多邊形、折線、
   雲線、便利貼（含註釋內容）、文字方塊（中英混排）、打字機、指示框、
   鉛筆筆畫、校正符號、圖章、檔案附件、量測線。
2. 用本程式加一個數位簽章（保護 → 數位簽署）。
3. 在簽章之後再加一則註解（測試增量寫入是否保住簽章）。
4. 用 Acrobat 開啟。

**通過判準**

- 開啟時**沒有任何警告或修復提示**。
- 每一種註解都畫得出來，且外觀與本程式一致（顏色、透明度、線寬、端點樣式）。
- 便利貼雙擊會開出註釋視窗，內容正確。
- 中文文字方塊的字**不是方框也不是亂碼**。
- 簽章面板顯示「**有效，簽署後有變更**」而不是「無效」。
- 檔案附件可以在 Acrobat 的附件面板看到並另存。

**失敗時**：把 Acrobat 的訊息與該註解的子型記進 `exceptions/`，並在矩陣的
對應需求備註寫明是哪一種註解、哪一個鍵。

## 2. 多螢幕與高 DPI（PRD-VIEW-006）

**為什麼自動化測不到**：需要兩台實體螢幕且 DPI 不同。虛擬螢幕無法重現
Windows 在跨螢幕拖曳時送出的 `QEvent::DevicePixelRatioChange` 序列。

**需要**：兩台螢幕，縮放比例不同（例如 100% 與 150%）。

**步驟**

1. 開一份含文字與圖片的 PDF，縮放到 100%。
2. 把視窗從 100% 的螢幕拖到 150% 的螢幕，中途停在跨越邊界的位置。
3. 拖回去。
4. 在 150% 螢幕上縮放到 400%，再拖回 100% 螢幕。

**通過判準**

- 頁面內容在跨越後**重新以新的裝置像素比渲染**，不是把舊圖磚拉伸
  （放大看文字邊緣：拉伸的結果會糊）。
- 縮放倍率的數字不變（版面維持邏輯像素）。
- 尺規刻度與頁面對齊，沒有偏移。
- 註解的位置與大小不變。

## 3. 螢幕閱讀器（PRD-A11Y-005 / A11Y-006）

**為什麼自動化測不到**：`tests/a11y` 驗的是 `QAccessibleInterface` 這一側
（名稱、角色、鍵盤可達性），那是必要條件不是充分條件。UIA 到 NVDA/JAWS
之間還有一層，而那一層只有真的用螢幕閱讀器才知道。

**需要**：NVDA（免費）或 JAWS。

**步驟**

1. 啟動螢幕閱讀器，開啟本程式。
2. 用 Tab 與 F6 走過整個視窗。
3. 開一份文件，用 PageDown 翻頁。
4. 開啟註解清單、書籤、Tags 面板，各走一遍。
5. 觸發「朗讀目前頁面」。

**通過判準**

- 每個工具列按鈕、面板、清單都被**念出名稱**，不是只念角色（「按鈕」）。
- F6 在面板之間循環，且念出面板名稱。
- 翻頁後念出「第 N 頁，共 M 頁，縮放 X%」。
- Ribbon 的分頁被念成分頁，不是一堆無名按鈕。
- 文件頁籤列被念成「開啟的文件」。

## 4. TSA 時間戳（PRD-SIG-006，R3）

**為什麼自動化測不到**：需要連到真實的 TSA 伺服器。CI 一律餵本地產生的
`TimeStampResp`，不連任何外部服務（見 `tests/ltv` 的說明）。

**需要**：一個可用的 RFC 3161 TSA URL，以及對外網路。

**注意**：時間戳屬 **R3**，依 CLAUDE.md 不提前實作。目前 UI 端會明確擋下
填了 TSA 網址的簽署請求（而不是靜默簽一份沒有時間戳的）。這一節記在這裡
是為了 R3 排到時有現成的步驟，不是現在要做。

## 5. 觸控目標尺寸（PRD-UI-013）

**為什麼自動化測不到**：44 CSS px 的等效換算已有測試，但「Ribbon 按鈕實際
算出來多大」取決於執行時的字型與 DPI。

**需要**：觸控螢幕（或以 Windows 的觸控模擬）。

**步驟**：在觸控螢幕上開啟本程式，逐一點擊 Ribbon 每個分頁的每顆按鈕。

**通過判準**：每顆按鈕都能一次點中，不需要瞄準；相鄰按鈕不會誤觸。

---

## 6. 十萬頁級記憶體（PRD-VIEW-001 的閒置記憶體上限）

**為什麼自動化測不到**：需要 10,000 頁的語料，產生成本高（磁碟與時間），
不適合每次 CI 跑。

**需要**：一份 10,000 頁的 PDF（可用 `tools/bench --generate` 加大頁數產生）。

**步驟**：開啟後捲到最後一頁再捲回開頭，靜置 60 秒，記錄工作集。

**通過判準**：閒置記憶體 ≤ 512 MB（PRD §8.1）。

## 7. 60 fps 捲動（PRD-NAV-002）

**為什麼自動化測不到**：需要在 GUI 事件迴圈上量幀率，而 `tools/bench`
刻意沒有事件迴圈（見它的 `notMeasured` 說明）。

**需要**：一份含大量向量圖的真實語料（工程圖最理想）。

**步驟**：以固定速度連續捲動 30 秒，用外部工具（例如 PresentMon）記錄幀率。

**通過判準**：P95 ≥ 60 fps，且沒有超過 16 毫秒的主執行緒阻塞。

## 8. PAdES-B 與 DocMDP（PRD-SIG-004 / SIG-007）

**為什麼自動化測不到**：我們自己的驗證器只證明「我們讀得回自己寫的東西」。
PAdES 的合規判定與 DocMDP 的「允許的變更」語意，最終裁決者是 Acrobat——
它對 `/DocMDP` 的 P 值解讀比規格文字嚴格，而寬鬆的一方不會有任何錯誤訊息。

**需要**：Adobe Acrobat（Reader 即可）。

**步驟**

1. 用本程式以 PAdES-B 建立一個簽章（保護 → 數位簽署）。
2. 用 Acrobat 開啟，看簽章面板的相容性描述。
3. 另建一份使用 DocMDP 的認證簽章，P 值分別試 1（不允許任何變更）、
   2（允許填表與簽署）、3（額外允許註解）。
4. 每一種 P 值之下，用本程式各做一次：加註解、填表單欄位、加頁面。
5. 每做一次就用 Acrobat 重新開啟，看簽章狀態。

**通過判準**

- PAdES-B 的簽章在 Acrobat 被認成有效，且不出現「此簽章格式不受支援」。
- P=1 之下任何變更都讓 Acrobat 顯示簽章**無效**（這是預期行為，不是缺陷）。
- P=2 之下填表不讓簽章失效，加註解會。
- P=3 之下填表與加註解都不讓簽章失效，加頁面會。
- 本程式的簽章面板對同一份檔案的判定與 Acrobat **一致**。判定不一致時，
  以 Acrobat 為準並建立 `exceptions/`。

## 9. 真實相容性語料庫（PRD §9 的 ≥ 300 份）

**為什麼自動化測不到**：現有的測試語料全部是我們自己產生的。自己產生的
語料只能驗證「我們寫得出來的東西我們讀得回來」，驗不到真實世界的 PDF——
而真實世界的 PDF 才是這個產品要開的東西。

**需要**：能合法散布或本機保留的真實檔案，以及存放的位置決策（見下方注意）。

**要收集的類別**（每一類至少 20 份，合計 ≥ 300）

| 類別 | 為什麼要它 |
|---|---|
| JBIG2 / JPEG2000 掃描件 | 兩種編碼都不在我們寫過的路徑上，解碼失敗會是整頁空白 |
| CJK 直排、直書標點 | 文字擷取的閱讀順序與選取錨點在直排下完全不同 |
| CAD 匯出的工程圖（A0、數千條向量） | 圖磚渲染與全文搜尋的效能預算就是為它訂的 |
| 含 XFA 的表單 | 必須走明確的降級提示，不得誤導使用者 |
| 含 3D / 內嵌 JavaScript | 同上；且必須確認 JavaScript 真的沒有被執行 |
| 加密（各種權限組合） | 權限旗標的行為分歧多，且失敗時不該讓使用者失去檔案 |
| 線性化與含 `/XRefStm` 的混合式 xref | 物件層寫入通道要在這三種形態上都產出零警告 |
| 破損 / 被截斷 / xref 錯誤 | 「不崩潰且明確說出問題」比「開得起來」重要 |
| 已簽章（各家工具產生） | 簽章驗證的正例必須來自別人，不能只有我們自己簽的 |

**步驟**

1. 依上表收集，每份記下來源與授權狀態。
2. 逐份執行：開啟 → 翻到最後一頁 → 全文搜尋一個常見字 → 加一則螢光筆 →
   存檔 → 重新開啟。
3. 記錄每一次的崩潰、明顯錯誤的畫面、以及任何靜默的內容遺失。

**通過判準**

- **零崩潰**。
- 不支援的特性（XFA / 3D / JavaScript）走明確的降級提示，不是靜默忽略。
- 存檔後重新開啟，內容與註解完整。
- 破損檔案給出可理解的錯誤，且原檔未被改動。

**注意**：多數真實 PDF 不能進版控（授權與體積）。語料庫應放在本機或內部
儲存並記錄清單，版控裡只留「清單與判定結果」。這個決策尚未拍板，屬於
`docs/CODE_REVIEW_2026-09-17.md` 建議順序第 5 項的一部分。

## 10. 發佈指標：主執行緒阻塞與安裝包大小

**為什麼自動化測不到**：主執行緒阻塞要在有事件迴圈的情況下量（與第 7 節
同一個理由）；安裝包大小要有實際的安裝檔，而封裝流程屬 WP8 尚未建立。

**需要**：目標機器一台；封裝完成後的安裝檔。

**步驟**

1. 開啟 500 頁 A0 工程圖，連續執行：翻頁、縮放、全文搜尋、加註解、存檔。
2. 全程以外部工具記錄主執行緒的單次最長阻塞。
3. 封裝完成後量安裝檔大小與安裝後的磁碟佔用。

**通過判準**

- 主執行緒單次阻塞 ≤ 16 毫秒（CLAUDE.md 的硬性限制）。
- 任務取消延遲 ≤ 16 毫秒。
- 安裝包 ≤ 130 MB（PRD §4.1）。

## 11. 快捷鍵與 Acrobat / PDF-XChange 對齊（PRD-UI-004）

**為什麼自動化測不到**：我們有快捷鍵表、衝突偵測與自訂介面，都有測試。
但「與 Acrobat 一致」是一個關於**別的程式**的事實，只能拿那個程式來對。

**需要**：Adobe Acrobat 與 PDF-XChange Editor 各一套（試用版即可）。

**步驟**

1. 在三個程式裡逐一按下同一個鍵，記錄各自的行為。至少涵蓋：
   單鍵工具捷徑（H 手形、V 選取、Z 縮放、C 註解）、Ctrl+O/S/P/F/G、
   F4、F6、Ctrl+Shift+加號（旋轉）、Ctrl+0/1/2（縮放預設）。
2. 把三欄並列成表。

**通過判準**

- 與 Acrobat 不一致的每一個鍵都有**寫下來的理由**（例如與本產品的既有
  功能衝突），而不是碰巧不一樣。
- 不一致的項目在偏好設定的「快捷鍵」頁可以改回去。
- 表本身存進 `docs/`，之後改鍵位時一併更新。
