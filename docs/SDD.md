## 1. 架構的三個約束

整個架構的形狀由三件事決定，其餘都是這三件事的推論。

### 1.1 PDFium 非執行緒安全

同一份文件把手在同一時間只能被一條執行緒觸碰。這不是效能建議，是資料損毀與當機的分界。

推論：

- 每個需要並行的子系統各自持有**獨立的文件把手與專用執行緒**，而不是共用一份把手加鎖。
  加鎖會讓所有子系統排隊在同一條臨界區上，等於沒有並行；而且鎖的粒度一旦寫錯，
  症狀是隨機的資料錯亂而不是死鎖，極難診斷。
- 目前有四個這樣的子系統：渲染（`alioth_engine`）、文字與搜尋（`alioth_text`）、
  註解寫入（`alioth_annotations`）、儲存（`alioth_save`）。
- 全域初始化只能有一次，由 `alioth_pdfium_runtime` 以引用計數集中管理。

代價是同一份檔案會被開啟多次。這是刻意的取捨：檔案是唯讀開啟（見 1.3），
重複開啟的成本遠低於共用把手帶來的正確性風險。

**修正（2026-09-06，ADR-005）：可以並存，不可以並行。**

上面那條「各自持有把手所以可以並行」的推論，經隔離量測證實是**錯的**。
拆開變因後的結果是：

- 四個擷取器同時活著、但嚴格輪流動作 → 完全正常（每個 10/10）。
  **多份把手同時存在沒有問題**，所以「各自持有把手」這半段成立，繼續照做。
- 兩條執行緒同時動作 → 非決定性地掉資料：第一輪 60/60、第二輪 5/60，
  之後整個行程的開檔開始失敗（錯誤碼 2 FORMAT）。**這半段不成立。**

原因是 PDFium 的行程級狀態（字型與模組快取）本身非執行緒安全，與把手無關。
它壞掉的方式是安靜地少給資料，不是崩潰——所以「跑起來沒事」不是證據。

因此：把手照樣一個子系統一份，但**任何時刻只能有一條執行緒在 PDFium 裡**。
需要加速的地方要改設計（例如全文搜尋改走預建索引），不能靠開更多執行緒。
恆真的兩條釘在 `tests/test_pdfium_concurrency.cpp`。

⚠️ 尚未處理：列印與檢視會真的同時動作（列印是長時間渲染，使用者同時還在捲動）。
目前沒有觀察到問題不等於安全，見 ADR-005 的「仍未處理的風險」。

### 1.2 記憶體預算來自可視區，不是文件大小

PRD §8.1 要求 500 頁工程圖閒置 ≤ 512 MB、10,000 頁文字型 ≤ 768 MB。
唯一能達成的方式是**只算看得到的部分**。

推論：

- 頁面切成 512×512 圖磚，只渲染與可視區相交者加外圍一圈預取
- 嚴禁整頁光柵化。唯一的例外是縮圖，因為它本來就是整頁的縮小版
- 圖磚快取是 LRU 加位元組預算（128–1024 MB），逐出以位元組計而不是以張數計
- 頁面把手也有常駐上限，按需載入、閒置釋放

### 1.3 存檔必須是純附加

「不破壞既有數位簽章」是產品的核心賣點（PRD-SIG-003）。數位簽章覆蓋的是
`/ByteRange` 指定的位元組區間，只要原檔位元組被改動一個，簽章就從
「有效、簽章後有變更」變成「無效」。

推論：

- 存檔一律走 `FPDF_SaveWithVersion` 的增量模式，並在寫出過程中**主動驗證**輸出前綴
  與原檔相同。不能只相信上游行為不變——PDFium 沒有版本承諾
- 落盤走「暫存檔 → flush → 原子更名」，斷電不得損毀原檔
- 開檔必須用 `FPDF_LoadCustomDocument` 搭配允許刪除／更名的檔案控制代碼。
  用 `FPDF_LoadDocument` 會持有獨占鎖，導致「檢視器開著文件時存檔」必定失敗——
  而那是存檔的唯一情境
- 復原一次附加式寫入 = 把檔案截回原長度，不需要整份快照。但截之前要比對邊界守衛

## 2. 分層

```
呈現層 (alioth_ui)          Qt Widgets：主視窗、Ribbon、檢視元件、停靠面板
    ↓ 只透過控制器
應用層 (alioth_app)         控制器、命令匯流排、復原堆疊、設定、跨執行緒編組
    ↓ 只透過引擎介面
領域層 (alioth_domain)      幾何、圖磚鍵、版面、註解模型、文字層模型
    ↑ 被所有層使用          純 C++，不依賴 Qt 也不依賴 PDFium
引擎轉接層 (alioth_engine 等) 唯一可以呼叫 PDFium 與 OpenSSL 的地方
    ↓ 只透過平台介面
平台層 (alioth_platform)    檔案 I/O、路徑、原子寫入。唯一可以有 #ifdef _WIN32 的地方
```

分層規則不是靠自律維持，是靠 CMake 的 target 相依關係強制的：

- 只有引擎層的 target 連結 `pdfium`。其他 target 出現 `target_link_libraries(... pdfium)`
  就是分層違規，而且會在 code review 前就被建置系統擋下來
- `alioth_domain` 不連結 Qt，因此領域層的測試不需要 `QApplication`，
  也保證核心模型可以在無 GUI 環境下驗證
- 引擎層不連結 Qt。路徑等字串以 `std::string`（UTF-8）傳遞，寬字元轉換收在平台層

### 2.0 引擎層的子系統切分

「引擎層」不是一個 target，是一組。每個子系統各自一個 static library，
邊界的判準只有一個：**它需不需要自己的 PDFium 文件把手與執行緒**。

| target | 連 PDFium | 存在的理由 |
|---|---|---|
| `Alioth::engine` | 是 | 渲染管線、圖磚、書籤讀取、連結。主要的文件把手 |
| `Alioth::text` | 是 | 文字擷取與搜尋。自己的把手，因為搜尋會長時間占用執行緒 |
| `Alioth::forms` | 是 | 表單填寫需要 PDFium 的表單環境（`FPDFDOC_InitFormFillEnvironment`） |
| `Alioth::signature` | 否（連 OpenSSL） | 簽章驗證是純位元組運算 |
| `Alioth::objects` | 否 | ADR-002 的物件層寫入通道。輸入位元組、輸出位元組 |
| `Alioth::annotations` | 部分 | 外觀串流產生（純運算）+ 舊的 PDFium 寫入路徑 |
| `Alioth::save` | 是 | 增量儲存、最佳化、加密檢查 |
| `Alioth::bookmarks` | 否 | 書籤與命名目標的讀寫。PDFium 讀不出縮放類型，也不能寫 |
| `Alioth::labels` | 否 | 頁面標籤 `/PageLabels`。PDFium 只給得出標籤字串，給不出範圍定義 |
| `Alioth::attachments` | 否 | 附件讀寫。PDFium 看不到檔案附件註解攜帶的那一份 |
| `Alioth::layers` | 間接 | `/OCProperties` 解析與圖層攤平（ADR-003 的還款）。自己沒有一行 PDFium 呼叫，但攤平重用 `Alioth::redaction` 的全檔重寫器，而後者公開連到 `Alioth::text`（連 PDFium）——建置圖上因此多一條間接邊，值得記著 |
| `Alioth::redaction` | 部分 | 塗黑：標記走文字外框（PDFium），套用走內容串流重寫 |
| `Alioth::compare` | 否 | 文件比對、尋找取代 |
| `Alioth::pageops` | 否 | 頁面組織的批次規劃與範圍運算 |
| `Alioth::enhance` | 部分 | 掃描增強、點陣化、影像重壓縮 |
| `Alioth::iosec` | 是 | 匯出影像與純文字 |
| `Alioth::formbuild` | 否 | 建立表單欄位 |
| `Alioth::print` | 否 | 列印版面與圖章內容串流 |
| `Alioth::create` | 否 | 從影像、文字、Markdown 建立 PDF |
| `Alioth::pages` | 是 | 頁面編輯（插入、刪除、旋轉、擷取）。結構性操作退回整份重寫時由它告知 |

**不連 PDFium 的子系統占多數**，這不是巧合：PDFium 是一個檢視器函式庫，
它的寫入 API 只覆蓋了它自己需要的那一小塊。凡是「PDF 規格有、PDFium 沒開放」
的東西，走 ADR-002 的物件層通道自己寫，反而比拼湊 PDFium 的特例 API 穩定。

### 2.1 為什麼領域層要 Qt-free

不是為了「將來換掉 Qt」——那個理由多數專案永遠不會兌現。真正的理由是
**測試成本**：領域層有座標轉換、版面計算、圖磚鍵、文字範圍這些純邏輯，
它們的正確性最需要密集測試，而 Qt Test 需要事件迴圈的部分會讓這類測試變慢且不穩。

## 3. 執行緒模型

| 執行緒 | 職責 | 同步機制 |
|---|---|---|
| GUI | 事件處理、可視區計算、圖磚合成、UI 狀態 | 只讀圖磚快取 |
| 渲染（每個文件一條） | 載入、圖磚渲染、註解讀取、書籤、縮圖 | 優先權佇列 + 取消權杖 |
| 文字（每個文件一條） | 文字層擷取、搜尋 | 同上，獨立的文件把手 |
| 儲存 | 增量儲存、自動儲存 | 在渲染執行緒上執行（需要同一份把手） |

### 3.1 佇列與取消

優先權三級：可見圖磚 > 預取 > 縮圖。同優先權維持先進先出。

取消有兩個時機：任務還在佇列裡（直接移除並回報 cancelled），或已經開始執行
（由呼叫端輪詢取消權杖）。**被丟棄的任務也必須回報**，不能靜默消失——
呼叫端通常在等一個回呼來更新狀態，少一次回呼就是一個永遠轉不完的載入指示器（IL-4）。

可見圖磚刻意**不給取消權杖**：它們就算來自上一幀，畫出來也是對的。
會被取消的是預取與縮圖。

### 3.2 跨執行緒編組

引擎回呼在引擎執行緒上被呼叫。應用層一律用 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`
排回 GUI 執行緒後才碰 UI 狀態。

控制器的解構必須**先關掉引擎**（`engine_.reset()`），因為成員的銷毀順序是宣告順序的反序，
而引擎執行緒的回呼會碰其他成員。這個坑已經在實作時踩過一次。

## 4. 渲染管線

```
可視區變更
   → 版面計算（domain::PageLayout）算出每頁在文件空間的矩形
   → 對每個可見頁：可視區裁進頁內 → 算出圖磚範圍
   → 查快取；未命中則排入佇列（可見）
   → 外圍一圈排入佇列（預取，可取消）
   → 引擎執行緒：FPDFBitmap_CreateEx 直接寫入 PixelBuffer（零複製）
   → 回呼寫入快取 → 排回 GUI 執行緒發出 tileReady
   → 呈現層以 QImage 包裝同一塊記憶體貼上（仍是零複製）
```

### 4.1 零複製的 stride

`FPDFBitmap_CreateEx` 的 stride 一律**顯式傳入**，禁止以「寬 × 4」推算。
BGRA 下兩者通常相等，但一旦引入對齊或子區域檢視就會不等，
而錯誤的 stride 產生的是**斜切畫面而不是崩潰**——這種錯誤在自動化測試裡極難察覺。

`QImage` 包裝引擎緩衝區時，以清理函式持有 `shared_ptr` 的一份拷貝，
確保圖磚被 LRU 逐出後那塊記憶體仍然有效。

### 4.2 縮放的兩階段圖磚鍵

圖磚鍵中的倍率是整數（倍率 × 1000），不是浮點——浮點的 1.2999999 與 1.3
是兩個不同的鍵，快取命中率會莫名其妙掉到零。

兩種鍵對應兩個階段：

- **縮放過程中**用等比階梯（1.1 的冪次）吸附後的鍵，整段縮放共用同一批圖磚。
  畫面上是暫時的拉伸結果，這是可接受的過場
- **縮放停止 80 毫秒後**用精確倍率鍵重算。PRD §4.3 明令「禁止以拉伸結果作為最終畫面」，
  這是那條規則的實作

縮放過程中不排預取：每個中間倍率都排一輪，等於把佇列灌滿註定要被丟棄的工作。

## 5. 註解子系統

```
文字選取 → QuadPoints（頁面座標）
   → domain::Annotation（幾何以 variant 表達，/Subtype 由幾何推導）
   → 外觀串流產生器（純函數，不碰 PDFium）
   → 註解寫入器（PDFium API，順序固定）
   → 增量儲存
```

### 5.1 為什麼必須自產外觀串流

PDFium 對多數註解型別**不會自動產生 `/AP`**。缺少它時 Acrobat 會自行補畫，
但 macOS 預覽與 Chrome 可能顯示不一致甚至完全不顯示。
「100% 相容 Acrobat」不只是把註解寫進 `/Annots`。

外觀串流產生器刻意做成純函數（輸入模型、輸出位元組），與 PDFium 完全隔離。
這讓它可以逐運算子驗證語法，而不必開啟一份 PDF。

### 5.2 已知限制

`FPDFAnnot_SetAP` 只建立 Form XObject 串流本身，**不建立 `/Resources`**，
因此串流內不能引用 `/ExtGState`，螢光筆的 Multiply 混合模式遺失，
`/Popup` 與 `/IRT` 也寫不進去。

處置是把降級明確回報到 UI 而不是靜默接受。根本解法需要自行輸出 PDF 物件層，
見 `exceptions/EXC_20260905_RD_SA_annot_ap_resources.md`，待 ADR 決定。

## 6. 座標系

三個座標系，轉換只准在一個地方發生。

| 座標系 | 原點 | Y 方向 | 單位 | 用途 |
|---|---|---|---|---|
| 頁面空間 | 頁面左下 | 向上 | 點（1/72 吋） | PDF 內的一切：`/Rect`、QuadPoints、字元外框 |
| 頁內裝置空間 | 頁面左上 | 向下 | 像素 | 圖磚座標、渲染矩陣 |
| 文件裝置空間 | 版面左上 | 向下 | 像素 | 捲軸位置、可視區、命中測試 |

- 頁面空間 ↔ 裝置空間的轉換**只准**經由 `domain::PageTransform`。
  它同時處理 Y 軸翻轉與旋轉；在別處自行翻轉會得到看似正確、實際上下顛倒的結果
- 頁內 ↔ 文件裝置空間只差一個平移，由 `domain::PageLayout` 提供
- PDFium 的渲染矩陣走的是頁面顯示空間（Y 已經向下），因此矩陣組裝時
  **不再翻轉一次**。兩邊都翻是最常見的錯誤

## 7. 錯誤處理

IL-4「失敗快失敗明」在本專案的具體含義：

- PDF 視為不可信任輸入。解析錯誤一律回傳明確的錯誤碼，不得回傳「成功但內容是空的」
- 非同步操作失敗也必須回呼，讓等待方能結束等待
- 降級（例如混合模式遺失）必須讓使用者看得見，不能只寫進 log
- 不可信任輸入決定的遞迴深度（書籤樹、大綱）一律改成迭代並設上限

## 8. 測試策略

| 層級 | 對象 | 做法 |
|---|---|---|
| 領域層 | 座標、版面、圖磚鍵、命令堆疊、文字範圍 | 純單元測試，無 Qt 事件迴圈 |
| 引擎層 | 開檔、渲染、取消、併發、增量儲存 | 以自產的最小 PDF 為語料，驗到像素與位元組 |
| 整合 | 選取 → 註解 → 存檔的核心迴圈 | 跨三個子系統，驗座標系假設一致 |
| 呈現層 | 開檔到圖磚上畫面 | offscreen 平台的冒煙測試 |
| 效能 | PRD §8.1 的指標 | `alioth_bench` 輸出 JSON，超出預算以非零碼結束 |

**測試語料自產、不依賴外部檔案**，讓測試能在乾淨的機器上跑。
真實的相容性語料（≥ 300 份，PRD §9）是驗收層級的事，不屬於單元測試。

已知不足：外觀串流尚未經 Acrobat 實機比對，qpdf 結構檢查未接，
效能數字只有合成語料。這三項是 M0 Gate 的未竟事項。
